用 LLM 构建 Coding Agent Lesson 02

Workflow vs Agent

何时才真的需要那个循环 —— 以及何时不该用它

第一课你已经知道：agent 的本质是「LLM 在循环里根据环境反馈调用工具」。 这节课回答一个更早、更重要的问题：什么时候你才真的需要这个循环？ 写 coding agent 的人常犯的第一个错，就是一上来就上循环、上框架，而其实一个简单方案就够了。

一个词：agentic systems，两个分支

Anthropic 把所有「让 LLM 干活的系统」统称为 agentic systems，但在架构上划出一条关键分界线：

Workflow（工作流）：LLM 和工具被预定义好的代码路径编排。 切几步、每步干什么、按什么顺序走 —— 都是你写死在代码里的。

Agent（智能体）：LLM 动态地自己指挥流程、自己决定用什么工具， 在「如何完成任务」上保有控制权。

分界线只有一句话：「下一步做什么」是谁决定的？ 写在你代码里的 if/else 和固定步骤 → workflow；由模型每一轮自己判断 → agent。 第一课那个 while 循环之所以是 agent，正因为循环里模型自己决定要不要再调工具、调哪个。

两者的取舍

WorkflowAgent
流程由谁定你的代码（预定义）模型（运行时动态）
给你什么可预测性、一致性灵活性、自主决策
适合定义明确、步骤能预测的任务开放式、步骤数无法预测的任务
代价不够灵活，遇到没写到的情况就卡住成本更高、可能错误累积、需要信任模型的判断
关键直觉：agent 用延迟和成本，换任务表现和灵活性。 只有当这个交换划算时才做。很多任务里它并不划算。

先别急着上循环：复杂度阶梯

Anthropic 给的核心建议是：先找最简单的方案，只在确实需要时才增加复杂度。 顺着这个阶梯，从下往上爬，能不上一层就不上：

  1. 单次 LLM 调用（配上检索和几个示例）—— 大多数应用到这层就够了。
  2. Workflow —— 任务需要多步但路径固定时，用预定义流程。可预测、好调试。
  3. Agent —— 只有当路径无法预先写死、需要模型在多轮里自主决策时，才上循环。

一句话决策：如果你能把步骤画成一张固定流程图，就用 workflow； 如果连有几步、每步干嘛都要看具体输入才知道，才需要 agent。

那 5 种 workflow 模式呢？

两个模式，正通向 agent

5 种模式里有两个，形状已经很接近 agent，值得你特别记住 —— 它们是 workflow 和 agent 之间的过渡带：

  • Orchestrator-Workers —— 中心 LLM 运行时动态拆解任务、分派、综合。 Anthropic 直接点名编码产品是典型场景：要改几个文件、每个怎么改，只有看了需求才知道，没法写死。 它和「并行化」长得像，但子任务是动态决定的 —— 这一步「动态」就是滑向 agent 的关键。
  • Evaluator-Optimizer —— 一个 LLM 生成、另一个评估给反馈，在循环里反复打磨。 它已经有循环了 —— 但注意：这个循环的结构（生成→评估→再生成）是你写死的。 agent 的循环则是模型自己驱动的。差别就在这。

workflow 的循环 vs agent 的循环：Evaluator-Optimizer 也有循环，但「转几圈、每圈干嘛」由你的代码定； agent 的循环里，这些由模型定。有没有循环不是分界线 —— 循环里谁做决定才是。

Coding agent 属于哪一类？

回到你的 mission。一个像 opencode / Claude Code 那样的 coding agent，属于真正的 agent。因为：

  • 用户说「修复这个 bug」时，没人能预先知道要读几个文件、改哪几处、跑几次测试。
  • 每一步都依赖上一步的环境反馈（报错、测试结果），下一步做什么得当场判断。
  • 步骤数完全开放 —— 可能 3 步搞定，也可能 20 步。这正是「无法写死路径」的开放式任务。

这也是为什么 Anthropic 说编码是 agent 的绝佳场景：代码可以自动验证（跑测试）， agent 能拿测试结果当反馈迭代，问题空间结构清晰，输出质量可客观衡量 —— 循环需要的「ground truth」它天然就有。

但别忘了阶梯：即使在 coding 领域，也不是所有功能都要 agent。 「把这段代码翻译成另一种语言」这种一步到位的任务，单次调用就够，硬套 agent 反而更慢更贵。 agent 留给那些「步骤无法预测」的开放式任务。

三条心法（贯穿全文）

  1. 能简单就别复杂 —— 从阶梯最低层开始，只在简单方案不够时才往上爬。
  2. 透明 —— 明确展示 agent 的规划步骤，别让它变黑盒（这也是为什么先别急着上框架）。
  3. 精心设计工具接口(ACI) —— agent 的能力上限，很大程度由工具的定义和文档质量决定。这是后面几课的重点。
