Workflow 模式速查卡

基于 Anthropic《Building Effective Agents》· 5 种可组合模式的压缩参考

Workflow = 预定义好的代码路径：切几刀、每步干什么、按什么顺序走，都写死在你的代码里。 模型只在每个格子里干活，不决定流程走向。这是它与 agent（模型自己决定下一步）的根本区别。

地基：Augmented LLM

所有 workflow 的基本积木：一个 LLM 单元，外挂三样能力。后面每次 LLM 调用都假设具备它们。

┌─ retrieval 检索：查外部知识 LLM ────┼─ tools 工具：调函数 / API └─ memory 记忆：记住信息

1. Prompt Chaining 提示链

输入 → LLM调用1 → [gate 检查] → LLM调用2 → 输出

何时用：任务能干净地拆成固定顺序的子步骤。用"多步、每步更简单"换更高准确率（牺牲延迟）。步骤间可加程序化关卡(gate)做检查。

例子：先写营销文案 → 再翻译；先写大纲 → 检查大纲合格 → 再写正文。

2. Routing 路由

┌─ 类型A → 专用 prompt A 输入 → 分类器 ┼─ 类型B → 专用 prompt B └─ 类型C → 专用 prompt C

何时用：输入有明显不同的类别、各自最好分开处理，且分类本身能做准。好处是关注点分离——不用一个万能 prompt 硬扛所有输入（优化 A 会拖累 B）。

例子：客服分流（咨询/退款/技术支持各走各的）；简单问题路由到便宜小模型、难问题路由到大模型省成本。

3. Parallelization 并行化

┌→ LLM(子任务1) ┐ 输入 ─┼→ LLM(子任务2) ┼→ 代码汇总 → 输出 └→ LLM(子任务3) ┘

何时用：子任务能拆开并行以提速，或需要多视角/多次尝试提高置信度。让每个考量点交给独立调用，各自专注，通常好过一个调用全揽。两个变体：

  • Sectioning（分片） — 切成互相独立的子任务并行跑。例：护栏（一实例回答、一实例筛查违规）；自动评估（每个调用评一个维度）。
  • Voting（投票） — 同一任务跑多次综合判断。例：多 prompt 从不同角度审代码找漏洞；内容审核用多票 + 不同阈值平衡误报漏报。
逻辑依赖 ≠ 执行串行。护栏和核心回答只依赖同一输入、互不依赖彼此输出，所以可以并行。 最终是否采用核心结果依赖护栏结论——那是结果依赖。
省钱 → 改串行：小模型护栏先过滤，被挡下的就不花大模型的钱；甚至用规则/moderation API 代替 LLM 护栏。
低延迟 → 并行：同时跑，但坏请求会白烧一次核心调用。

4. Orchestrator-Workers 编排者-工人

┌→ worker(子任务1) ┐ 输入→编排者┼→ worker(子任务2) ┼→ 编排者综合 → 输出 └→ worker(子任务?) ┘ ← 数量/内容运行时才定

何时用：复杂任务且子任务无法预先预测——要几个子任务、各干什么，看具体输入才知道。中心 LLM 动态拆解、分派、综合。

与并行化的关键区别：拓扑相似，但并行化的子任务是你预先切好的；这里是编排者运行时临时决定的。

例子：编码任务（改几个文件、怎么改取决于需求，没法写死）；跨多来源搜集分析的搜索任务。

5. Evaluator-Optimizer 评估者-优化者

生成器 → 结果 → 评估器 ─满意─→ 输出 ↑______反馈(不满意，附改进意见)__│

何时用：满足两条件：(1) 有清晰的评估标准；(2) 迭代改进能带来可衡量提升。信号：人给反馈能明显改进结果，且 LLM 也能给出这种反馈。类比人类反复修改文章。

例子：文学翻译（初译漏语感，评估者批评后再改）；需多轮搜索分析的复杂检索（评估者判断是否再搜）。

选择表

你的任务特征用哪个
能拆成固定顺序的几步Prompt Chaining
有明显不同类别、要分开处理Routing
子任务预先可切、彼此独立Parallelization · Sectioning
同一任务想多跑几次求稳Parallelization · Voting
子任务运行时才知道有哪些Orchestrator-Workers
有明确标准、值得反复打磨Evaluator-Optimizer

贯穿全文的三条心法

  1. 能简单就别复杂 — 先试最简单方案（优化单次调用 + 检索 + 示例）。很多应用不需要 workflow，更不需要 agent。
  2. workflow vs agent 的取舍 — workflow 给可预测性和一致性（定义明确的任务）；agent 给灵活性和自主决策（开放式、步骤不可预测），代价是更高成本与错误累积。
  3. 只在"可衡量地改善结果"时才加复杂度 — 这些模式是可组合、可裁剪的套路，不是教条。
对写 coding agent 的启发： Orchestrator-Workers 被文档直接点名"编码产品"是典型场景（改几个文件、怎么改运行时才定）。 Evaluator-Optimizer 的"生成→评估→反馈→再生成"循环已很接近 agent loop —— 区别在 workflow 的循环结构是你写死的， agent 的循环由模型自己驱动。
